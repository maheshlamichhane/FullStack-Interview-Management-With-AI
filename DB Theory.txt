SQL Statement Execution Process:

1. Parser
-> Syntax & semantic validation.
-> Checks SQL grammer
-> Verifies
	* Table names exists
	* Column names exist
	* Data type are valid
-> Converts SQL text into a parse tree

Example:
SELECT * FROM orders ORDER BY order_id;

Parser breaks it into
* SELECT clause
* FROM clause
* ORDER BY clause
* Table: orders
* COlumn: order_id

-> If syntax is wrong -> error stops here


2. Rewriter
-> Logical rewriting
-> What it does
	* Applies rules before optimization
	* Expands: Views,Rules,Inheritance
-> Rewrites query into an equivalent logical form.

Example:
SELECT * FROM active_orders;

If active_orders is a VIEW
SELECT * FROM orders WHERE status = 'ACTIVE';
Rewriter replaces it correctly


3. Optimizer(Planner)
-> Find the cheapest execution plan
-> This is the most important stage
-> Key rule: Lower cost always wins

-> Generates multiple possible plans
-> Calculates cost for each
-> Chooses the lowest-cost plan

Cost depends on
-> Table size
-> Index availability
-> Data distribution
-> Disk vs memory access
-> Parallelism



4. Executer
-> Execute the choosen plan
-> Executes plan node by node
-> Performs
	* Table scans
	* index lookups
	* Joins
	* Sorting
-> Reads/Writes actual data pages
-> Only one plan reaches executer
-------------------------------------------------------------------------

1. Sequential Scan:
EXPLAIN SELECT * FROM orders;
-> PostgreSQL reads every rows from the orders table.
-> No index is used
-> Fast when: table is smalll and large% of rows are needed.

Seq Scan on orders

EXPLAIN SELECT * FROM orders WHERE order_id IS NOT NULL;

Why still Sequential Scan??
-> order_id IS NOT NULL matches alsmost all rows
-> Index gives no selectivity
-> Planner prefers sequential read
=> Index is ignored intentionally

2. Index Nodes:

	* Heap file -> actual table data
	* Index file -> pointers to heap rows


i. Index Scan:

Explain SELECT * FROM orders WHERE order_id=1;
-> Search index for order_id = 1
-> Get row pointer(TID)
-> Fetch row from heap table

Index Scan using idx_orders_id on orders

-> Best for highly selective queries.


ii. Index Only Scan

EXPLAIN SELECT order_id FROM orders WHERE order_id=1;

Why This is faster
-> Required columns(order_id) exists only in index
-> PostgreSQ checks visibiity map
-> No heap access required.

Index Only Scan using idx_orders_id on orders

-> Fasterst scan type



iii. Bitmap Index Scan:
SELECT * FROM orders WHERE country = 'Nepal';
-> Execution steps
	* Scan index -> build bitmap in memory
	* Combine multiple matches
	* Fetch heap pages in optimized order

Bitmap Index Scan
-> Best when
	* Many rows match
	* Low-cardinality columns



3. Join Nodes:
-> Join always operate on two inputs.
-> Multiple joins are executed step by step.
-> Output of one join feeds the next.


i. Nested Loop Join:
-> How it works
For each row in table A
Find matching rows in table B

Plan:
Nested Loop
	-> Index scan

Best When:
-> Outer table is small
-> Inner table has index

-> Bad for large datasets


ii. Hash Join:
-> Build hash table from smaller input
-> Probe hash table with larger input

Plan:
Hash Join
	-> Hash

Best for:
-> Large tables
-> Equality joins(=)


iii. Merge Join
-> Both inputs must be sorted
-> Reads rows in order and merges

Plan:
Merge Join

Best for:
-> Pre-sorted data
-> Range joins

Index Types:

i. B-Tree Index
-> Balanced tree data structure
-> Height stays small -> logarithmic time
-> Default index type in PostgreSQL

CREATE INDEX idx_employee_id ON employee_practise(id);

-> What B-Tree Supports
	* Equality(=,IN)
	* Range(<,>,<=,>=,BETWEEN)
	* Ordering(ORDER BY)

-> Why primary keys use B-Tree
	* Fast lookups
	* Enforces uniqueness
	* Sorted order helps joins and ranges


ii. Hash Index
-> Uses hash function
-> Direct bucket lookup
-> Only supports equality

CREATE INDEX idx_employee_email_hash ON employee_practise USING HASH(email);

-> Supported operators(=)
-> Important Limitations
	* No range scans
	* No ordering 
	* Rarely faster than B-Tree
	* Cannot enforce uniqueness




iii. BRIN INDEX(Block Range Index)
-> Indexes ranges of blocks not rows
-> Stores min/max value per block range

CREATE INDEX idx_orders_date_brin ON orders USING BRIN(order_date);

-> Why BRIN is Powerful
	* Tiny index size
	* Very fast to build
	* Cheap to maintain
	* Ideal for huge tables

-> When BRIN works best
	* Data is naturally ordered
	* Values increase over time

-> Examples Order_date,created_at
-> When BRIN is BAD
	* Random data
	* Frequent updates
	* Small tables



iv. GIN Index
-> Indexes elements inside a column
-> One column value -> Many index entries

CREATE INDEX idx_tags_gin ON articles USING GIN(tags);

-> Best suited for
	* Arrays
	* JSONB
	* Full-Text Search

Example:
tags TEXT[];

ACID Properties


i. Atomicity
-> A transaction is atomic, meaning it either fully happens or does not happen
at all.
-> If any part of a transaction fails, all changes are rolled back.
-> Ensures partial updates do not happen.

Example:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id=1;
UPDATE accounts SET balance = balance + 100 WHERE id=2;
COMMIT;

-> IF the second update fails:
	* Without atomicity -> money dissapears(bad)
	* With atomicity -> first update is rolled back

-> Database treats the transaction as a single unit.
-> Impemented via rollback/commit.



ii. Consistency(Data Integrity)
-> After a transaction, the database must remain in a valid state, respecting all
rules,constraint and integrity.
-> Examples of constraints
	* Primary Key
	* Foreign Key
	* Check constraints
	* Triggers
-> Transactions cannot violate these rules.
-> Example: Balance must always be >= 0
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
If balance < 100 -> transaction fails
Database rejects invalid state, keeping integirty

-> Consistency ensures business rules are enforced.
-> Usually enforced automatically by DBMS constraints.


iii. Isolation
-> Each transaction is isolated from others as if it runs alone.
-> Prevents dirty reads,non-repetable reads, and phantom reads.

a. Read Uncomitted
-> It enables dirty reads
-> Lowest isolation, rarely used.

-> Here transaction can see uncommitted changes from other transactoins.
-> Rarely used in practise.
-> PostgreSQL ignores this and treats as READ COMMITTED.

Note: It does not solve any problem like dirty read,non-repeatable read,phantom read.


b. Read Committed
-> Dirty reads prevented
-> Default in Postgresql

-> Each query sees data committed before the query started.
-> Uses MVCC snapshots per query, not per transactions.


Note: It solves Dirty read but non repeatable read and phantom read can occurs.


c. Repeatable Read
-> Dirty + non-repeatable reads prevented
-> Transaction see consistent snapshots.

-> Uses MVCC snapshot per transaction.
-> The transaction sees the database state as of the start of the transaction.
-> Rows read once will always return the same value, even if other transactions commit changes later.

Note: It solves dirty read and non-repeatable read but phantom read can occurs.

d. Serializable
-> Full isolation
-> Highest safety,slowest

-> PostgreSQL simulates transactions running one after another(series execution).
-> Detects conflicts at commit time and may abort a transaction to prevent 
anomalies.
-> Prevents phantom insert by tracking reads and writes.


iv. Durabiity
-> Once a transaction is committed, changes are permanent,even if the syste
crashes immediately afterward.
-> Impemented using
	* Write-Ahead Logging(WAL)
	* Disk flush
-> Gurantees no data loss after commit.

Example:
BEGIN
INSERT INTO orders(id,customer_id,total) VALUES(1,101,500);
COMMIT;

-> Even if the server crashes after COMMIT, the order is safely stored on disk.

Dirty Read
-> A dirty read occurs when a transaction reads data that has been modified by
another transaction that has not yet been committed.
-> IF the other transaction rolls back, the first transaction has read invalid data.
-> Dirty reads violate isolation.
-> They can only happens in READ UNCOMMITTED isolation level.


Non-Repeatable Read
-> A non-repeatable read occurs when a transaction reads the same row twice but
another transaction modifies or delete that row in between.
-> Happens in READ COMMITTED isolation level.
-> The row is real, but inconsistent within the transaction.


Phantom Read
-> A phantom read occurs when a transaction reads a set of rows matching a condition,
but another transaction inserts or delete rows that match that condition
before the first transaction ends.
-> Happens in REPEATABLE READ, but PostgreSQL's REPEATABLE READ actually prevents it by using MVCC and Serializabe sanpshots.
-> Phantom rows are "new" or "dissappered" rows.


Since In Prod We used READ COMMITTED then how non-repeatable read and phantom read is
handled??
-> Even though READ COMMITTED doesn't prevent them, they are often controlled at
the application level or via propert transaction design.

Non-Repeatable Reads
-> It is handled in production

1. Small, quick transactions:
	* Most OLTP apps keep transaction very short(few milliseconds).
	* The chance of a non-repeatable read causing issues is small.
2. Applicaiton logic
	* Read -> check -> update is often done in a single query or with optimistic
	locking.ensures you never rely on a stale read; the update fails safely if data
	changed
	Example:
	Uses
		UPDATE accounts
		SET balance = balance - 100
		WHERE id = 1 AND balance >= 100;
3. Optimistic concurrency control.
-> Add a version/timestamp column to detect changes between reads and writes.


Phantom Reads
-> It is handles in production
1. Design queries to be single-statement where possible.
	* Avoid multiple SELECTS in one transaction if the row set can change.
2. Locks for critical operations
	* PostgreSQL supports SELECT ... FOR UPDATE/FOR SHARE.
	SELECT * FROM orders WHERE customer_id > 100 FOR UPDATE;
	* Prevents other transactions from inserting rows that would match your query
	until you finish.

Pessimistic Locking:
-> Pessimistic locking assumes conflicts are likely, so it locks rows before
modifying them, preventing other transactions from accessing them until the lock
is released.
-> PostgreSQL uses row-level lock with SELECT ... FOR UPDATE or SELECT ... FOR SHARE
-> Other transactions trying to update or lock the same rows wait until the lock
is released.
-> Ensures no two transactions modify the same row concurrenlty.

Types of locks:

i. FOR UPDATE -> Lock row for update - other transactions wait.
ii. FOR NO KEY UPDATE -> Similar, but allows foreign key references
iii. FOR SHARE -> Prevents updates but allows reading.
iv. FOR KEY SHARE -> Less strict, allows concurrent operations.

Example:
BEGIN;
SELECT balance FROM accounts WHERE id=1 FOR UPDATE;
COMMIT:

Pros
-> Simple and predictable
-> Prevents concurrency conflicts at the database level.

Cons
-> Can cause blocking and deadlocks.
-> Reduces concurrency for high-traffic apps.



Optimistic Locking:
-> Optimistic locking assumes conflicts are rare. Transactions don't lock rows while
reading; they check for conflict before commiting.

How it works in PostgreSQL

1. Add a version or timestamp column to the table.
ALTER TABLE accounts ADD COLUMN version INT DEFAULT 1;

2. Read the row(no lock)
SELECT balance,version FROM accounts WHERE id=1;

3. Update only if the version hasn't changed:
UDPATE accounts SET balance = balance - 100, version = version+1 WHERE id =1 AND version =1;
-> If the row was modified by another transaction zero rows are updated 
-> Application detects this adn retries transaction.

Pros
-> No waiting or blocking
-> High concurrency possible
-> Useful when conflicts are rare.




Shared Lock
-> A shared ock allows multiple transactions to read the same resource concurrently,
but prevents conflicting writes.
-> Multiple transactions can hold a shared lock simultaneously.
-> Blocks exclusive operations(like UPDATE,DELETE,or explicit exclusive lock).
-> Commony used in SELECT ... FOR SHARE or foreign key checks.

Example:
Transaction A
BEGIN;
SELECT * FROM accounts WHERE id = 1 

Transactoin B
BEGIN;
SELECT * FROM accounts WHERE id =1 FOR SHARE;

-> Both transaction can read the row
-> But if Transaction B tries to UPDATE the same row -> it waits until both shared
locks are released.



Exclusive Lock
-> An excusive lock precents other transactions from reading or writing the locked
resournce in a conflicting way.
-> Acquired automatically by UPDATE,DELETE or INSERT.
-> Only one transaction can hold an exclusive lock on the same row at a time.
-> Blocks both other exclusive and conflicting locks.

Example:
Transaction A
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

Transaction B
BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 1;

-> Row is locked exclusively by Transaction A.
-> No other transactoin can update or acquire conflicing lock until commit/rollback.

Deadlock
-> A deadlock occurs when two or more transactions are waiting for each other to
release locks, and none of them can proceed.
-> Both transaction are blocked forever unless PostgreSQL intervenes.
-> Common in concurrent update scenarios.
-> Suppose we have a table accounts
id        balance
1 		  100
2 		  200

Transaction A:
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;

-> Transaction A ocks row 1

Transaction B
BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 2 ;

-> Transaction B locks row 2.

Now both transaction try to update the other row

Transaction A:
UPDATE accounts SET balance = balance - 10 WHERE id = 2;

Transaction B:
UPDATE accounts SET balance = balance - 20 WHERE id = 1;

Result: both transactions are waiting on each other -> deadlock



How PostgreSQL detects deadlocks:
-> PostgreSQL has a deadlock detector that:
	* Periodically checks for cycles in the wait for graph.
	* If it finds a scycle, it aborts one of the transactions.
-> The aborted transaction receives an error:


How PostgreSQL detects Deadlocks:
-> Abort one transaction(victim) to break the deadlock.
-> other transaction proceed.
-> Aborted transactions must retry if needed.

Common Causes of Deadlocks:
1. Concurrent updates in different order
	* Transaction A locks row1 -> row2 
	* Transaction B locks row2 -> row1

2. Pessimistic locking(SELECT ... FOR UPDATE)
	* If multiple transation lock rows in different orders, deadlock occurs.
3. Foreign key checkls
	* Updating parent and child tables concurrently can cause locks to wait.
4. Unique constraint or indexes
	* Inserting rows with the same index concurrently can cause lock conflicts.



How to prevent deadlocks in PostgreSQL
1. Lock rows in consisten order
-> Always access rows in the same order in all transactions.
-- Correct order
UPDATE accounts SET balance = balance - 50 WHERE id IN (1,2) ORDER BY id;

2. Keep transaction short
-> The less time a transaction holds locks,the lower the chance of deadlocks.

3. Use optimistic locking for low-contention updates
-> Avoid holding locks while performing application logic.
-> Detect conflicts via version column instead.

4. Catch deadlock erros and retry
-> If a transaction fails due to deadlock, retry automatically.
